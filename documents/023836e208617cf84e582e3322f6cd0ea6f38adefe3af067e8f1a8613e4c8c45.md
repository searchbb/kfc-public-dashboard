[p006]
该功能的核心价值是解决缓存失效的排查痛点。此前如果请求未命中缓存，开发者只能看到`cache_read_input_tokens`降为0，没有任何提示说明prompt的哪部分发生了变动。新功能上线后，只要请求未命中缓存，就能直接看到具体的变动位置，以及这次缓存失效带来的token损耗。

[p007]
功能入口为Claude控制台的用量缓存页面：https://platform.claude.com/usage/cache，完整官方文档可参考：https://platform.claude.com/docs/en/build-with-claude/cache-diagnostics

[p009]
为了兼顾普通用户的理解，先简单解释Prompt缓存的作用：这是Claude降低API调用成本、缩短响应延迟的核心功能，只要两次请求的prompt前缀完全一致（字节级匹配），就能复用之前的缓存，前缀部分的token不用重复计费，响应速度也会快很多。

[p010]
但这个匹配规则非常严格，哪怕只是系统提示词里多了个自动插入的时间戳、工具列表的顺序换了、消息历史里多了个空格，都会直接导致缓存失效。此前没有任何官方排查工具，很多开发者遇到成本突然暴涨的情况，只能逐行对比prompt，效率极低。

[p011]
### 功能使用说明（面向开发者）

[p012]
目前该功能处于beta阶段，调用Claude API时需要带上beta头`cache-diagnosis-2026-04-07`，每次请求的参数中带上上一次响应返回的`previous_message_id`，API就会自动对比两次请求的结构差异，在响应的`diagnostics`字段中返回缓存未命中的原因。

[p013]
具体流程如下：每次对话都要携带beta头，第一轮请求传入`previous_message_id: null`完成功能启用，后续每轮请求都把上一轮响应的id传入，API会对比两次请求并返回第一个差异点。

[p014]
下面是官方文档给出的Python基础调用示例：

[p015]
client = anthropic.Anthropic()

[p016]
SYSTEM = "You are an AI assistant analyzing a large document. <document>...</document>"

[p017]
# Turn 1: opt in with previous_message_id=None  
    r1 = client.beta.messages.create(  
        model="claude-opus-4-7",  
        max_tokens=1024,  
        cache_control={"type": "ephemeral"},  
        system=SYSTEM,  
        messages=[{"role": "user", "content": "Summarize section 1."}],  
        diagnostics={"previous_message_id": None},  
        betas=["cache-diagnosis-2026-04-07"],  
    )

[p018]
# Turn 2: reference the previous response id  
    r2 = client.beta.messages.create(  
        model="claude-opus-4-7",  
        max_tokens=1024,  
        cache_control={"type": "ephemeral"},  
        system=SYSTEM,  
        messages=[  
            {"role": "user", "content": "Summarize section 1."},  
            {"role": "assistant", "content": r1.content},  
            {"role": "user", "content": "Now summarize section 2."},  
        ],  
        diagnostics={"previous_message_id": r1.id},  
        betas=["cache-diagnosis-2026-04-07"],  
    )

[p019]
diagnostics = r2.diagnostics  
    if diagnostics is None:  
        print("No divergence detected.")  
    elif diagnostics.cache_miss_reason is None:  
        print("Comparison still pending.")  
    else:  
        print(f"cache_miss_reason: {diagnostics.cache_miss_reason.type}")

[p020]
如果使用流式响应，`diagnostics`信息会放在`message_start`事件中，示例代码如下：

[p021]
# Turn 2: stream, referencing the previous response id  
    with client.beta.messages.stream(  
        model="claude-opus-4-7",  
        max_tokens=1024,  
        cache_control={"type": "ephemeral"},  
        system=SYSTEM,  
        messages=[  
            {"role": "user", "content": "Summarize section 1."},  
            {"role": "assistant", "content": r1.content},  
            {"role": "user", "content": "Now summarize section 2."},  
        ],  
        diagnostics={"previous_message_id": r1.id},  
        betas=["cache-diagnosis-2026-04-07"],  
    ) as stream:  
        for text in stream.text_stream:  
            print(text, end="", flush=True)  
        print()  
        r2 = stream.get_final_message()

[p022]
diagnostics = r2.diagnostics  
    if diagnostics is None:  
        print("No divergence detected.")  
    elif diagnostics.cache_miss_reason is None:  
        print("Comparison still pending.")  
    else:  
        print(f"cache_miss_reason: {diagnostics.cache_miss_reason.type}")

[p023]
目前支持的失效原因包括：

[p024]
* 模型变动：两次请求调用的模型不一致，通常是路由、A/B测试或降级逻辑切换了模型
  * 系统提示词变动：系统提示词内容有变化，通常是插入了时间戳、请求ID等动态内容
  * 工具列表变动：工具的增删、排序变化，或者工具参数的JSON序列化格式不一致
  * 消息历史变动：消息列表的内容、顺序有调整，比如截断了历史、重新序列化了助手返回内容

[p025]
返回结果同时会包含估算的失效token量，方便开发者评估损失。一个典型的失败响应结构如下：

[p026]
{  
      "id": "msg_01Xyz...",  
      "type": "message",  
      "role": "assistant",  
      "content": [{ "type": "text", "text": "..." }],  
      "usage": {  
        "input_tokens": 42,  
        "cache_read_input_tokens": 0,  
        "cache_creation_input_tokens": 41850,  
        "output_tokens": 210  
      },  
      "diagnostics": {  
        "cache_miss_reason": {  
          "type": "system_changed",  
          "cache_missed_input_tokens": 41850  
        }  
      }  
    }

[p027]
可以结合`diagnostics`结果和实际缓存命中情况判断问题：

[p028]
诊断结果| 缓存读取token数| 结论  
---|---|---  
null| 高| 一切正常，前缀稳定且命中缓存  
null| 低或零| 请求结构没变，但缓存已过期，缩短请求间隔即可  
存在*_changed类型结果| 低或零| 请求结构变动导致未命中，按提示修复对应位置  
存在*_changed类型结果| 高| 变动发生在较晚位置，靠前断点仍然命中，修复优先级较低

[p030]
1. 目前仅支持Claude原生API，不支持亚马逊Bedrock、谷歌Vertex AI上托管的Claude版本
  2. 用于对比的请求指纹有留存时间限制，仅支持同组织、同工作区内的请求对比
  3. 超长对话的深度差异可能无法精确识别，会返回不可用状态
  4. 诊断功能为尽力实现，不会阻塞正常请求，若无法获取诊断信息会返回对应状态码

[p031]
另外值得一提的是隐私策略：该功能符合零数据保留标准，不会存储你的原始prompt和响应内容，仅存储由哈希和token估算值组成的请求指纹，且指纹会在短时间后过期删除。

[p033]
这条功能公布后，引发了大量AI从业者的讨论，不同用户的需求差异非常明显。

[p034]
不少做生产级AI应用的开发者给出了极高的评价，认为这是Claude近期最有实用价值的更新：之前把带缓存的prompt推到线上，完全是"盲飞"状态，不知道什么时候命中率就掉了，能精确看到变动点对成本优化的价值非常大。

[p035]
有开发者调侃，终于能看清自己的token到底是在哪被"烧"没的。

[p036]
还有开发者提出了更进一步的需求：既然都能定位到缓存失效的原因，为什么不能自动做兼容，优先复用未变动部分的缓存？

[p037]
不管反响如何，这也是Claude对于token用量的一个回应，对于想要明明白白使用的开发者是个好消息。
