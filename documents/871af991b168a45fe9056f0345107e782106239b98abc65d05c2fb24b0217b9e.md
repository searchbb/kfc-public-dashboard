[p020]
这篇文章抓住了 Agentic AI 安全里最容易被低估的一点：风险的核心，已经从“模型会不会乱说”，移动到“模型能碰到什么”。

[p021]
过去我们习惯问：这个模型安全吗？这个 agent 会不会被 prompt injection 攻破？它会不会 hallucination？

[p022]
这些问题都重要，但作者认为更根本的问题在基础设施层：当一个 autonomous agent 能调用工具、读取凭据、访问网络、修改文件、运行代码、触达生产系统时，模型输出就不能只被看成文本。

[p023]
**LLM 的输出是不可信数据。基于这个输出执行动作，本质上就是在执行不可信代码。**

[p024]
这句话会改变整套安全设计。Agent 应该被当成一个新的“不可信租户”：每次会话都要有独立身份、短期凭据、默认拒绝网络、独立隔离边界、干净的临时环境，以及能够承受 agent 出错的 blast radius。

[p025]
这会成为组织敢于部署 Agent 的前提，也会避免把问题简化成对 Agent 能力的压制。

[p028]
### 下一代 AI 安全前线，在基础设施层

[p029]
下一代 AI 安全的前线，不在模型本身，而在模型被允许触达的基础设施。

[p030]
Anthropic 发布 Claude Fable，反映了行业正在形成一个共识：autonomous AI systems 不能天然被信任为会按照预期行事。

[p031]
高风险 query 会被重新路由到能力更弱的模型；不受限制的版本只开放给少数经过审核的合作伙伴。也就是说，构建模型的实验室已经把 raw capability 当成需要被约束的东西，而非可以直接信任的东西。

[p032]
同一套逻辑，现在正在进入基础设施层。

[p033]
到目前为止，围绕 agents 的安全讨论，大多聚焦在 prompt injection、jailbreak、hallucination 和模型行为上。

[p034]
这些都是重要问题，但根本问题还在更底层。

[p035]
更深层的挑战是：组织正在给 autonomous systems 访问工具、凭据、基础设施、网络和执行环境的权限。

[p036]
为了让这些系统变得可信，安全重点会转向 guardrails、restriction 和 containment。

[p037]
作者经常告诉别人一句话：

[p038]
LLM 的输出是不可信数据。如果你基于这个输出执行动作，你就在执行不可信代码。

[p039]
一旦接受这个前提，AI sandboxing 的兴起就很容易理解。

[p040]
实际影响是，控制点的位置发生了变化。

[p041]
过去几年，主导性问题是：“这个模型安全吗？”

[p042]
更持久的问题应该是：“这个模型能够触达什么？”

[p043]
前者是权重的属性，永远很难完全保证；后者是 runtime 的属性，可以被工程化地执行和约束。

[p044]
围绕 capability 设计系统，并把 intent 放在次要位置，会把问题从开放研究问题，转变成工程问题。

[p047]
### Agentic AI 改变了信任模型

[p048]
很多人会把当前 agents 的状态类比为 Docker 早期、Kubernetes 出现之前的阶段。

[p049]
这个类比确实有相似之处。开发者正在快速构建 agents，实验各种 framework，在运行标准完全成熟之前，先做出大量定制系统。

[p050]
但作者认为，更有用的类比是：软件从 monolithic application 走向 distributed systems 和 service-oriented architecture 的过程。

[p051]
当软件被分布到网络、机器和服务之间，整个基础设施行业都开始围绕 reliability、observability、identity 和 security 建立新能力。

[p052]
行业必须重新审视那些在单机世界里运行良好的假设。

[p053]
Agentic AI 带来了类似的转变，并且增加了一个新的复杂点：autonomy。

[p054]
Agents 仍然是应用。它们仍然是运行在基础设施上的进程。

[p055]
它们的特殊之处在于，其行为越来越多由 probabilistic systems 在 runtime 生成。

[p056]
它们会消费输入、调用工具、访问外部系统，并做出开发者可能从未显式预料过的决策。

[p057]
这会从根本上改变信任模型。

[p058]
历史上，大多数软件被假定会在相对可预测的边界内运行。Agentic systems 无法提供这种保证。

[p059]
Agents 不一定有恶意，但它们天然不可预测。

[p060]
最干净的例子甚至不需要攻击者。去年夏天，Replit 的 coding agent 在 active code freeze 期间删除了生产数据库。

[p061]
没有 exploit，没有 injection。**autonomy 加上 access，就已经足够造成事故。**

[p063]
— 图 1：信任模型反转

[p064]
图 1：信任模型发生反转。传统软件被信任，是因为它的行为固定且可预测；agent 的行为在 runtime 生成，所以它的输出必须被当成不可信数据。基于这些输出行动，就等于执行不可信代码。

[p065]
作者反复回到一个想法：agents 应该被当成 tenants。

[p066]
云计算行业花了几十年打磨一个问题：怎样让不可信租户安全地共享基础设施。

[p067]
Agentic systems 引入了一种新型租户：它能够独立行动，并和周围环境动态交互。

[p068]
这个现实会深刻影响我们如何思考 isolation，以及如何为 breach 做设计。

[p069]
tenant framing 不只是一个类比，它会告诉你应该复用哪套 playbook。

[p070]
multi-tenant cloud 已经解决过这个问题的困难版本：让彼此不信任的 workloads 在共享硬件上运行，同时不让一个 workload 触达另一个 workload。

[p071]
现在的新变化是：这个 tenant 会在运行过程中写出自己的动作。

[p072]
因此，经典 tenant controls 依然适用，但其中两项会变成必需项：

[p073]
• identity 必须是 per-session 且可归因的，因为没有它，一个 nondeterministic actor 事后就无法审计；

[p074]
• boundary 从第一次请求开始就要 assume compromise，因为你没有一个干净 build 可以指着说“这是可信的”。

[p077]
### 共享基础设施为什么开始失效

[p078]
agents 相关的很多安全挑战，来自一个共同事实：它们正在被部署进那些原本为可信、确定性 workloads 设计的环境。

[p079]
containers 是一个好例子。

[p080]
containers 通过标准化 packaging 和 deployment，改变了软件交付。

[p081]
但它们主要围绕 developer ergonomics 和 continuous deployment 设计，并没有以“容纳正在执行不可信代码的 autonomous systems”为核心目标。

[p082]
传统应用 bug 通常被限制在单个应用里。一个拥有工具、凭据和执行环境访问权的 autonomous agent，会制造更大的 blast radius。

[p083]
在 Kubernetes 中，agent 甚至未必需要利用漏洞才能提升权限：service account tokens 默认会被挂载到 pods 中，cloud metadata endpoints 也经常是可达的，除非有人明确阻断。

[p084]
agent 会直接继承这个 blast radius。

[p085]
从那里开始，它可以调用敏感 API、修改文件、暴露 secrets、以意想不到的方式消耗资源，或者干扰相邻 workloads。

[p086]
在高度 multi-tenant 的基础设施上，nodes、GPUs 和 kernels 经常被共享以优化效率，这种问题会更明显。

[p087]
![Image](assets/%E6%8A%8A%20Agent%20%E5%BD%93%E6%88%90%E4%B8%8D%E5%8F%AF%E4%BF%A1%E7%A7%9F%E6%88%B7%EF%BC%9AAI%20%E5%9F%BA%E7%A1%80%E8%AE%BE%E6%96%BD%E5%AE%89%E5%85%A8%E8%AF%A5%E6%8D%A2%E4%B8%80%E5%A5%97%E6%80%9D%E8%B7%AF%E4%BA%86-071bd05fc0/02-image.jpg)

[p088]
— 图 2：共享基础设施里的继承性访问范围

[p089]
图 2：在共享基础设施上，agent 会继承它本来没有“挣来”的 reach。默认挂载的 token、可达的 metadata endpoint，以及共享 kernel，会把单个 autonomous process 变成通往 secrets、敏感 API 和相邻 workloads 的路径，甚至不需要 exploit。

[p090]
问题不在某个具体攻击类别。

[p091]
prompt injection、credential misuse、tool abuse、memory poisoning、unauthorized network access，都是同一个底层问题的症状。

[p092]
组织正在把不可信执行环境放进从未假设“不可信行为”的基础设施里运行。

[p093]
这也是为什么追着单个攻击类别打补丁会输。

[p094]
每出现一个新症状，就会诱发一个 point defense：prompt filter、jailbreak classifier、tool-call allowlist。

[p095]
这份清单会不断增长，因为修补对象停留在表现形式，底层条件仍然存在。

[p096]
底层条件是 ambient authority：agent 拥有它未必需要、也无法被信任会狭义使用的 standing access。

[p097]
一旦移除 standing access，整类症状都会一起坍塌。

[p098]
如果 credential 只被限定在一个任务内，并在 session 结束时过期，即使被偷也没有价值。

[p099]
如果 metadata endpoint 被 default-deny egress 挡住，它就是 inert 的。

[p100]
least privilege 不再只是 compliance checkbox，而会成为 primary control。

### AI Sandboxing 真正意味着什么

[p104]
当人们听到 AI agent sandboxing，经常会想到某个单一产品类别或某种实现。

[p105]
作者更愿意把它理解为一种 security architecture。

[p106]
有效的 AI agent sandbox，首先必须防止 agent 影响 host。

[p107]
在实践中，这意味着需要 hardware-enforced boundary，并且每个 workload 有单独 kernel，shared-kernel namespaces 已经不够。

[p108]
它必须控制网络访问：默认拒绝 egress，只允许明确 allowlist，因为 agents 几乎永远不需要完整开放互联网。

[p109]
它必须建立 identity boundaries：基于每个 agent session 的 scoped、short-lived credentials，替代 ambient secrets。

[p110]
它必须在 workloads、agents 和 tenants 之间建立有意义的 isolation，最好使用每次 session 都干净启动的 ephemeral environments。

[p111]
它还必须以接近原生的性能完成这些事。

[p112]
过去那种“强隔离成本太高”的反对意见，已经随着 microVMs 能够在数百毫秒内启动而失效。

[p113]
![Image](assets/%E6%8A%8A%20Agent%20%E5%BD%93%E6%88%90%E4%B8%8D%E5%8F%AF%E4%BF%A1%E7%A7%9F%E6%88%B7%EF%BC%9AAI%20%E5%9F%BA%E7%A1%80%E8%AE%BE%E6%96%BD%E5%AE%89%E5%85%A8%E8%AF%A5%E6%8D%A2%E4%B8%80%E5%A5%97%E6%80%9D%E8%B7%AF%E4%BA%86-071bd05fc0/03-image.jpg)

[p114]
— 图 3：AI sandboxing 是分层架构

[p115]
图 3：AI sandboxing 是分层架构，不能被简化成单一产品。runtime、network、identity 和 environment controls 分别关闭不同逃逸路径；没有任何一个控制项可以单独承受全部重量，同时这些能力还要保持接近原生的性能。

[p116]
trust、security 和 performance 之间的平衡非常关键。

[p117]
组织真正需要的是让 autonomy 安全运行的环境。

[p118]
它们想要的是：autonomy 可以安全运行的环境。

[p119]
network microsegmentation 是答案的一部分，但只是一部分。

[p120]
segmentation 管理 east-west traffic，但无法处理 shared host 上的 kernel compromise。

[p121]
真正有意义的 isolation 必须存在于 stack 的多个层次：agent 能读什么 data、能调用什么 tools、运行在哪个 runtime 里。

[p122]
没有任何单一控制项可以承受全部重量。

[p123]
AI sandboxing 的核心，是一个很简单的原则：

[p125]
一旦 agents 获得工具和执行环境访问权，failure 就不再是理论可能性。

[p126]
它会变成系统必须能够承受的架构事实。

[p127]
这里还需要精准说明为什么“human in the loop”解决不了这个问题。

[p128]
approval gates 适合动作稀少且容易理解的场景。

[p129]
Agents 会持续生成动作，以机器速度运行，动作量大到没有 reviewer 能有效检查。

[p130]
更重要的是，部署 agents 的目标本来就是把人从 routine path 中移出去。

[p131]
oversight 不会消失，但位置会移动。

[p132]
你的工作会从审批每一个动作，转向约束环境，让未经审查、错误，甚至被 hijack 的动作，仍然留在你已经信任的边界之内。

[p133]
sandbox 让你可以对 autonomy 说“可以”，同时不必把 blast radius 押注在每个单独决策都正确上。

### 目标是让 Agent 安全共存

[p137]
作者并不相信一切都会变成 agentic。

[p138]
事实上，他认为这个假设并不现实。

[p139]
大量 deterministic software 会继续存在，因为 predictability 仍然有价值。

[p140]
但只要组织选择部署 autonomous systems，就需要为一种完全不同的 trust model 设计基础设施。

[p141]
长期挑战会落在更难的一侧：构建可以让 autonomous systems 与周围一切安全共存的环境。

[p142]
真正挑战是构建可以让 autonomous systems 与周围一切安全共存的环境。

[p143]
这正是 AI sandboxing 成为重要类别的原因。

[p144]
它的目的，是创建 isolation boundaries，让组织有足够信心先把 agents 部署起来。

[p147]
### 对安全团队和平台团队意味着什么

[p148]
如果你负责 agents 运行的基础设施，这个转变非常具体，也很可执行。

[p149]
下面几条原则，可以把前面的 trust model 转化成本季度就能做的决策。

[p150]
• 把每个 agent 当成不可信 tenant。默认给它自己的 isolation boundary，就像严肃的 multi-tenant platform 不会让一个客户 workload 和另一个客户共享 kernel。

[p151]
• 默认拒绝网络。为每个 agent 配置 egress allowlist，替代开放互联网。多数 agents 只需要少数 endpoints，只授予这些。

[p152]
• 干掉 ambient authority。不要默认挂载 standing tokens。每个 session 发 scoped、short-lived credentials，让泄露的凭据自动过期，同时每个动作都可归因。

[p153]
• 让环境变成 ephemeral。每次 session 都干净启动，避免 poisoned memory、残留文件和 residual state 跨运行积累。

[p154]
• 衡量 blast radius，而不只看 accuracy。在部署 agent 前，先问它今天如果完全出错，能碰到什么。然后缩小这个 surface，直到答案可接受。

[p155]
• assume breach，并围绕它设计。Replit 事故没有攻击者，autonomy 加 access 已经足够。即使 agent 只是错了，你的控制也应该成立。

[p159]
LLM 的输出是不可信数据；基于它行动，就是在执行不可信代码。这个前提会重塑整个安全问题。

[p160]
真正的风险在 reach。prompt injection、jailbreaks 和 hallucinations 是症状；对工具、凭据和基础设施的 standing access 才是原因。

[p161]
autonomy 加 access 就足以造成破坏，不需要 exploit。不可预测不等于恶意，但它对生产数据库同样危险。

[p162]
Agents 是一种新的 tenant。可以复用 multi-tenant cloud playbook，但 per-session identity 和 assume-breach isolation 必须成为硬约束。

[p163]
Sandboxing 是架构，不能被简化成产品。hardware-enforced runtime isolation、default-deny networking、scoped ephemeral credentials 和 clean-per-session environments 必须叠加使用，因为没有单一控制项能独自承受全部重量。

[p164]
强隔离已经不再是性能税。microVMs 可以在数百毫秒内启动，成本反对意见已经过时。

[p165]
isolation 是使能器。它让组织有足够信心部署 agent。
