# Claude Agent Platform 深度解析：基础设施、架构模式与工程实践

[p002]
> 来源：[原文链接](https://mp.weixin.qq.com/s/RKld5EYZ1NvFdDsD_GwJuA)

[p003]
引言：从 API 到「云上的计算机」理解 AI Agent Platform 的演进，需要回溯近几年的技术迭代路径。在 GPT-3 时代，AI 平台只是一个「补全端点」——你发送一段 prompt，收到一段回复，就此结束。随后有了对话会话和工具调用。再然后，有了 Claude Managed Agents：云端的一台计算机，配有持久内存和完整的状态管理。这条演进轨迹的深层逻辑是：随着模型能力越来越强、越来越自主，平台需要提供越来越高阶的抽象，但始终围绕一个目标——让用户以最少的工作量获得最好的结果。Anthropic 平台团队的产品和工程负责人在 Code with Claude 活动中，系统性的揭示了 Claude Agent Platform 的设计哲学，覆盖平台架构设计、基础设施关键挑战、多智能体编排模式、Agent 生命周期管理以及未来演进方向、那些让大多数 Agent 项目死在生产环境的基础设施挑战、以及多智能体编排的前沿实践。

[p004]
# 1\. 平台演进：从 Completion Endpoint 到 Managed Agent

[p005]
理解 Claude Agent Platform 的当前形态，需要先理解它是怎么一步步走到这里的：

[p006]
## 1.1 演进阶段

[p007]
阶段| 形态| 关键能力  
---|---|---  
**第一代**|  Completion Endpoint| 文本补全，调用一次返回一次  
**第二代**|  有状态的 Messages API| 会话持久化，跨请求的状态保持  
**第三代**|  工具调用 (Tools)| 代码执行、网页搜索、文件操作  
**第四代**|  Managed Agents| 云端计算机 + 内存 + 会话管理 + 安全沙箱  
每一次演进，平台承接了更多之前需要开发者自行构建的能力。Anthropic 团队指出：

[p008]
> **"平台最终会变成一组原语和基础设施，让你以最快速度、最少工作量获得结果。"**

[p009]
这个定义把平台的本质说得很清楚：平台不是功能集，而是阻力最小化的路径。

[p010]
## 1.2 Claude Managed Agents 的原语设计

[p011]
![Image](assets/Claude%20Agent%20Platform%20%E6%B7%B1%E5%BA%A6%E8%A7%A3%E6%9E%90%EF%BC%9A%E5%9F%BA%E7%A1%80%E8%AE%BE%E6%96%BD%E3%80%81%E6%9E%B6%E6%9E%84%E6%A8%A1%E5%BC%8F%E4%B8%8E%E5%B7%A5%E7%A8%8B%E5%AE%9E%E8%B7%B5-1412f6f2f7/01-image.png)Claude Managed Agents 并非另起炉灶，它建立在和所有用户一样的 Messages API 之上，然后在其上构建了一层封装：内置原语包括：

[p012]
* Messages API：所有能力的基础，包含 token 输入输出
  * 内置工具：代码执行（在沙箱中生成并运行）、网页搜索、文件操作等
  * File System 访问：Claude 风格的统一文件系统抽象
  * Skills：可复用的工作流剧本，按需加载
  * MCP 服务器：扩展与外部工具和数据源的集成
  * Vaults：安全存储认证凭证和密钥
  * Sandbox：安全的隔离执行环境
  * Session 管理：持久化会话状态

[p013]
Anthropic 的做法是：对某些原语有强约定（比如文件系统操作、Skills），因为他们相信这是 Claude 风格的正确做法；同时对其他部分保持灵活性，允许用户替换和扩展。

[p014]
# 2\. 基础设施之墙：大多数 Agent 项目死于这里

[p015]
![Image](assets/Claude%20Agent%20Platform%20%E6%B7%B1%E5%BA%A6%E8%A7%A3%E6%9E%90%EF%BC%9A%E5%9F%BA%E7%A1%80%E8%AE%BE%E6%96%BD%E3%80%81%E6%9E%B6%E6%9E%84%E6%A8%A1%E5%BC%8F%E4%B8%8E%E5%B7%A5%E7%A8%8B%E5%AE%9E%E8%B7%B5-1412f6f2f7/02-image.png)

[p016]
## 2.1 所有人都遇到的墙

[p017]
Anthropic提到了一个反复从客户那里听到的现象：

[p018]
> **"原型阶段进展神速，大家都兴奋不已，觉得 AI 真的在做事了。然后——把它投入生产并规模化的时候，所有人都会撞上同一堵基础设施之墙。"**

[p019]
这堵墙的具体构成包括：

[p020]
* 永远在线的服务器：你需要一台持续运行的服务器（或容器）来托管 Agent
  * 弹性的扩缩容：负载是动态的，你需要能 spin up / spin down 的基础设施
  * Transcript 数据存储：Agent 与用户的历史对话需要持久化，跨会话保持上下文
  * 安全的沙箱隔离：Agent 执行代码、访问文件系统时需要安全隔离
  * 连接稳定性：沙箱连接断开 Agent 就死掉；你需要处理这种脆弱性

[p021]
这不是 harness 调优的问题，而是生产级系统必须解决但大多数团队没有精力解决的问题。

[p022]
## 2.2 Claude Code 与 Managed Agents 的分工

[p024]
* Claude Code：面向个人开发者的强力工具，可以跑 Agent，适合快速原型和单个开发者的工作流
  * Claude Managed Agents：面向团队和企业，提供生产级基础设施——持久化、扩缩容、安全沙箱、凭证管理

[p025]
> **"基础设施部分，是大多数人最终撞上的那堵墙，但他们原本预期的是 harness 工程和模型调优才是更难的部分。"**

[p026]
这也是为什么 Anthropic 选择把 Managed Agents 做成一站式服务——因为他们自己在内部迭代了足够多轮，已经把「如何让 Agent 在云端可靠运行」这件事想清楚了。

[p027]
# 3\. Harness 与模型的耦合：新一代架构趋势

[p028]
![Image](assets/Claude%20Agent%20Platform%20%E6%B7%B1%E5%BA%A6%E8%A7%A3%E6%9E%90%EF%BC%9A%E5%9F%BA%E7%A1%80%E8%AE%BE%E6%96%BD%E3%80%81%E6%9E%B6%E6%9E%84%E6%A8%A1%E5%BC%8F%E4%B8%8E%E5%B7%A5%E7%A8%8B%E5%AE%9E%E8%B7%B5-1412f6f2f7/03-image.png)Anthropic有一个非常重要的技术判断——Harness 与模型正在从解耦走向紧耦合。

[p029]
## 3.1 旧范式：Generic Harness + Hot-Swap Models

[p030]
几个月前，标准做法是构建一个非常通用的 harness，然后可以在不同模型之间 hot-swap。这种做法对于上一代模型来说基本可行，因为模型之间的差异没有那么大。

[p031]
## 3.2 新范式：Harness + Model 作为整体单元

[p032]
Anthropic团队指出了当前行业正在发生的变化：

[p033]
> **"每个实验室（Anthropic、OpenAI、Google 等）在推进模型能力时采用了不同的技术路径。理论上你可以做一个覆盖所有模型的 superset harness，但实际上，当你为你的公司或客户交付最终成果时，你不会在 harness 层做 generic hot-swap。你会把 harness 和模型配对成一个整体单元来做。"**

[p034]
与此同时 Anthropic 也从自己的实验数据印证了这个观点：

[p035]
> **"我们最近在做 Managed Agents 的 Memory 实验。我们尝试了多种不同的 harness，结果发现——在同一个模型上，不同 harness 的表现差异巨大。Eval 评测结果差距大到惊人。"**

[p036]
这意味着：光换模型不够，你需要针对特定模型做 harness 工程优化。这是一个巨大的 Alpha 来源——每个实验室、每个 provider 的模型都有其独特的 harness 最优配置。Cursor 这样的产品可能就在走这条路：不是做 generic harness hot-swap，而是针对每个模型单独优化 harness，然后根据场景选择合适的「模型+harness」组合对外提供服务。

[p037]
# 4\. 多智能体编排：架构模式与最佳实践

[p038]
Anthropic 刚刚发布的 multi-agent orchestration 功能，访谈揭示了其中几种核心架构模式。

[p039]
## 4.1 核心编排模式

[p040]
模式一：Advisor Strategy（执行与建议分离）将生成者和建议者分开：一个 Agent 负责生成方案，另一个 Agent 负责审查和提供建议。这有助于打破「生成者偏见」，让建议者更客观地评估方案质量。模式二：Adversarial Pairs（对抗性配对）一个 Agent 生成内容，另一个 Agent 以对抗性视角挑战它。适用于需要高质量输出的场景，比如代码审查、策略评估。这种结构让缺陷在内部就被暴露出来，而不是等到人工 review 时才发现。模式三：Swarms（蜂群式分工）将任务分解为多个小片段，并行处理，然后再重新组合。适合 bug hunting 等需要广度探索的任务。模式四：Best-of-N生成 N 个不同的方案，然后通过某种评估机制选最优。

[p041]
## 4.2 不同模式对应的任务类型

[p042]
模式| 最佳适用场景  
---|---  
Advisor Strategy| 代码审查、策略评估、需要独立第二意见的场景  
Adversarial Pairs| 架构评审、高风险决策、安全审查  
Swarms| Bug hunting、漏洞扫描、多角度探索  
Best-of-N| 创意生成、设计方案评估、代码实现对比  
Anthropic的观点是：如果原语设计得足够像乐高（模块化），人们可以把它们组合成更高阶的架构和策略，获得更有趣的结果。这说明平台设计的目标不是提供终极解决方案，而是提供高质量的模块，让用户在其上构建自己的最佳实践。

[p043]
# 5\. 团队 Agent：从个人工具到组织级基础设施

[p044]
## 5.1 个人生产力与团队级 Agent 的本质区别

[p045]
当被问到「为什么不能直接用 Claude Code 来替代团队 Agent」时，Anthropic给出了一个关键区分：个人生产力工具的问题：

[p046]
* Agent 运行在个人笔记本上，无法 24/7
  * 多用户无法共享同一个 Agent 实例
  * 跨团队协作和审批流程无法标准化

[p047]
团队级 Agent 必须具备的能力：

[p048]
* 始终在线（always-on）
  * 多用户并发交互
  * 跨团队边界工作（市场→法务、工程师→CI/CD）
  * 可配置的安全和权限边界

[p049]
## 5.2 Anthropic 法务团队的实际案例

[p050]
Anthropic 内部有一个非常实际的案例：法务团队用 Agent 审查市场部门的文案。工作流是：

[p051]
* 市场人员写完文案，提交给这个 Agent
  * Agent 做第一轮审查，标记出潜在的法律风险
  * 如果 Agent 判断可以放行，文案直接通过
  * 如果 Agent 判断需要人工审查，则推送到法务团队的收件箱

[p053]
* 这不是一个 Skill，而是一个完整的 Agent：因为它需要持久化的会话状态、需要 MCP 服务器访问外部数据、需要凭证管理、需要人工审核的交互界面
  * 需要 Human-in-the-loop：完全自动化法律审查不现实，法务团队需要保留最终审批权
  * 在团队内部形成协作闭环：市场 Agent → 法务 Agent → 人工复核，形成完整的跨部门工作流

[p054]
## 5.3 Agent 所有权与持续演进

[p055]
一个非常实际的组织问题：

[p056]
> **"如果没有人对 Agent 负责，它很快就会过时。然后它就变成了一个废弃的东西，在那做着事情但不产出价值。"**

[p057]
Anthropic 的实践是：

[p058]
* Agent 有明确的所有者：市场团队拥有市场 Agent，法务团队拥有法务 Agent
  * 非技术人员也能改进 Agent：任何人发现 Agent 的问题，可以直接用 Claude Code 打开它，提交 PR 来改进它
  * 中间层抽象保护非技术用户：普通用户通过与「Claude 对话」来与 Agent 交互，而不是直接操作底层代码；这防止了非技术人员做出破坏性修改

[p059]
这个设计的精妙之处在于：它是 managed agents all the way down——最上层是用户直接对话的简单界面，底层是多个 Managed Agents 在相互协作处理复杂任务，中间通过 prompt 来调节每个 Agent 的行为范围。

[p060]
# 6\. Agent 生命周期管理：老化、退役与自我进化

[p061]
![Image](assets/Claude%20Agent%20Platform%20%E6%B7%B1%E5%BA%A6%E8%A7%A3%E6%9E%90%EF%BC%9A%E5%9F%BA%E7%A1%80%E8%AE%BE%E6%96%BD%E3%80%81%E6%9E%B6%E6%9E%84%E6%A8%A1%E5%BC%8F%E4%B8%8E%E5%B7%A5%E7%A8%8B%E5%AE%9E%E8%B7%B5-1412f6f2f7/04-image.png)

[p062]
## 6.1 Agent 过时的问题

[p063]
> **"Agent 会过时。有时候是因为没有人类附着在上面，有时候是因为它们跑的是旧模型或者旧架构。我觉得需要给 Agent 办个葬礼，在公司网站上放一个 '已退役 Agent 列表' 页面。"**

[p064]
这揭示了一个真实的工程问题：当你在生产环境中跑着几十个 Agent，新模型发布后，这些 Agent 如何升级？如果没有系统性的升级流程，老 Agent 会逐渐失效，变成数字僵尸。

[p065]
## 6.2 升级路径与最佳实践

[p066]
Anthropic 提供的解决方案包括：Skill 驱动的自动化迁移：当新模型发布时，使用专门的升级 Skill 来帮助完成 Agent 的迁移过程。这降低了升级的操作成本。Agent 监控 Agent：最激进的 AGI 团队已经在实践——用 Agent 来监控 Agent 的健康状态和性能，检测到过时时自动触发升级流程。Eval 驱动的回归验证：在升级前后运行相同的 eval suite，确保新模型+harness 的组合不比旧的差。这是系统性升级的基础设施。

[p067]
## 6.3 平台的目标：Outcome + Budget

[p068]
Anthropic团队反复提到的一个概念是：Agent 的成功应该用 Outcome（结果）和 Budget（预算）来衡量，而不是用中间指标。

[p069]
> **"我们真正的目标是：给 Claude 一个目标和一个预算，它就能完成它。'帮我赚十亿美元，预算是一千万美元'——这就是未来的形态。"**

[p070]
这个理念压缩了 Agent 的评价维度：不再关注调用了几次、token 消耗多少、跑了多长时间，而是关注「你交代的任务完成了没有，资源有没有超支」。这是对 Agent 价值的最本质衡量方式。

[p071]
# 7\. 平台架构：设计哲学与未来演进

[p072]
## 7.1 当前架构的分层设计

[p073]
*   *   *   *   *   *   *   *   *   *   *

[p074]
┌─────────────────────────────────────┐│         User Interface              │  <- 用户直接交互的层（Slack、Claude Chat 等）├─────────────────────────────────────┤│       Managed Agent (Thin Layer)    │  <- 包装用户体验的薄层├─────────────────────────────────────┤│  Multi-Agent Orchestration Layer    │  <- 多 Agent 编排（Advisor/Adversarial/Swarm 等模式）├─────────────────────────────────────┤│   Claude Managed Agents primitives  │  <- Skills、MCP、Vaults、Sandbox、Session 等├─────────────────────────────────────┤│        Messages API + Model         │  <- 底层 Messages API + Claude 模型└─────────────────────────────────────┘

[p076]
* 每层都可以独立演进
  * 原语层（底层）保持稳定，上层可以快速迭代
  * 用户不需要理解底层复杂性和基础设施的脆弱性

[p077]
## 7.2 未来一年：Claude 写自己的 Harness

[p078]
![Image](assets/Claude%20Agent%20Platform%20%E6%B7%B1%E5%BA%A6%E8%A7%A3%E6%9E%90%EF%BC%9A%E5%9F%BA%E7%A1%80%E8%AE%BE%E6%96%BD%E3%80%81%E6%9E%B6%E6%9E%84%E6%A8%A1%E5%BC%8F%E4%B8%8E%E5%B7%A5%E7%A8%8B%E5%AE%9E%E8%B7%B5-1412f6f2f7/05-image.png)Anthropic 描述了一个令人振奋的未来方向：

[p079]
> **"我们想实验的方向是：让 Claude 足够了解自己，以至于它能自己判断应该用哪个模型、能自己 spin up 所有的子 Agent。在那个世界里，你不需要去想 harness 工程的事，也不需要去想工具怎么构造。今天你不需要想太多关于 prompt 工程的事；但越往上走，会有更多这样的事被自动化。"**

[p081]
* Model Selection 自动化：Claude 根据任务性质自动选择合适的模型
  * Sub-agent Orchestration 自动化：Claude 根据任务需求自动拆分和调度子 Agent
  * Harness Engineering 自动化：Claude 能够动态构建适合自己的执行 harness

[p082]
> **"你不需要去想现在该用什么架构，因为 Claude 已经足够了解自己，可以动态调整。"**

[p083]
同时也调了平台扩展性的重要性：

[p084]
> **"如果 Agent 不断运行、不断重建自己、不断伸缩——系统必须能够处理这种粒度的负载。这意味着平台需要能够处理 long-running 请求、多种形状的任务、弹性的扩缩容。"**

[p085]
这是一个重大的工程挑战：不是为了每秒处理多少请求而扩展，而是为了「Agent 永不停机地运行、随时创建和销毁子会话」这种新型工作负载而扩展。
