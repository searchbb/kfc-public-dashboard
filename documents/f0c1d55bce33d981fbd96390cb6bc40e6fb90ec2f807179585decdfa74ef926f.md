# Claude Code 为什么缓存命中率能做到 92%？一篇讲清 Prompt Caching 的工程逻辑

[p002]
> 来源：[原文链接](https://mp.weixin.qq.com/s/2nlmjrz-6giYyzuVRGIDOQ)

[p003]
很多创业团队在复盘时都会发现一个尴尬的现象：AI 确实提高了生产力，但成本却吞噬了所有的利润。尤其是像 AI 编程、自动化工作流这类重上下文的场景，随着对话轮数的增加，API 调用成本呈指数级增长。这让很多开发者陷入了矛盾：想要 AI 更聪明，就得给它塞更多资料；但给的资料越多，钱包缩水的速度就越快。难道高性能与低成本真的不可兼得吗？Anthropic 在设计 Claude Code 时，其实已经给出了标准答案。他们并不是在做慈善，而是在利用一种极度严苛的‘物理规则’来重塑商业闭环。为了看清这背后的真相，我们先来看一个真实发生的案例。![Image](assets/Claude%20Code%20%E4%B8%BA%E4%BB%80%E4%B9%88%E7%BC%93%E5%AD%98%E5%91%BD%E4%B8%AD%E7%8E%87%E8%83%BD%E5%81%9A%E5%88%B0%2092%25%EF%BC%9F%E4%B8%80%E7%AF%87%E8%AE%B2%E6%B8%85%20Prompt%20Caching%20%E7%9A%84%E5%B7%A5%E7%A8%8B%E9%80%BB%E8%BE%91-657c6fa105/01-image.png)一、先看一个账单上个月有个朋友跑来问我，说他用 Claude Code 搞了一下午，账单出来傻眼了——200 万 input token，按 Sonnet 的标准价算下来接近 $6，但他同事做同样的任务只花了不到 $1.2。两个人用的同一个模型，同一个项目，差距接近 5 倍。差别就在于缓存命中率。他同事跑了一下 token 明细，发现 92% 的输入都是从缓存里读的——真实计费只有那 8% 的新内容，加上一开始写入缓存的那一次费用，算下来 $1.15。这 92% 不是运气，也不是随便调个参数调出来的。它是整套工程设计的产物。 今天我想把这件事从头讲清楚。

[p005]
二、你可能没意识到的一个问题在我们正式谈缓存之前，先得理解 LLM API 有多"笨"。它没有记忆。每次你发一条消息，客户端都会把完整的对话历史重新打包发过去。你的第 20 条消息，附带的不是"第 20 条"，而是前面 19 条对话加上系统提示加上工具定义，全部一起发。模型每次都要从头重新读一遍，就好像刚认识你一样。这在普通聊天场景里还好，上下文不长，费用也有限。但 Claude Code 这类 AI 编程工具，情况完全不同。它需要把系统提示、工具定义、CLAUDE.md 项目配置全部装进上下文。光这些静态内容就能轻松超过 20,000 token。加上每一轮对话积累的文件读取内容、工具调用结果，跑到第 30 轮，输入可能已经 40 万 token 了。而其中 39 万，是你上一轮已经发过的东西。没有缓存的情况下，那 39 万 token 都按全价计费，产生的价值是零。这就是为什么 Prompt Caching 在 Agentic 场景里不是锦上添花，而是商业模型成立的前提。

[p007]
三、Prompt Caching 到底在缓存什么？很多人以为这是某种"记住对话"的功能，其实不是。LLM 在推理时，内部有一个叫 KV Cache（Key-Value Cache）的结构，存的是注意力机制（Attention）对每个 token 的中间计算结果。正常情况下，这些中间结果用完就丢了，下次请求要全部重算。Prompt Caching 做的事是：把这份中间计算结果保存下来，如果下次请求的前缀跟之前一模一样，就直接复用，不用重算。注意"前缀"这个词。匹配规则是从头开始的严格前缀匹配，不是模糊匹配。系统对你发来的 token 序列做哈希，只要前 N 个 token 的哈希对上了，后面的内容就从缓存里读。但凡这 N 个 token 里有任何一个字节改变了——哪怕是一个空格、一个大写字母——整个缓存就作废，全部重算。这个特性是理解 Claude Code 所有工程决策的基础。定价也很简单：写入缓存是标准价的 1.25 倍（贵一点，因为要存），从缓存读是标准价的 10%（便宜 10 倍）。缓存默认保存 5 分钟，每次命中会刷新计时，也可以花更多钱延长到 1 小时。算账的话，只要后续有 1 次命中，写入的成本就已经回本了。

[p009]
四、Claude Code 的设计逻辑：围绕"缓存稳定性"展开Anthropic 内部有个工程师叫 Thariq Shihipar，他在采访里说过一句话，大意是：Prompt Caching 是 Claude Code 整个产品架构的核心约束。他们会在缓存命中率下跌的时候拉 SEV（严重事故）。所以 Claude Code 不是"用了 Prompt Caching"，而是整个产品是围绕"怎么让缓存一直命中"来设计的。它的上下文结构，从稳定到动态，严格分层：

[p010]
[工具定义]                 ← 最稳定，会话开始就定好  
    [系统提示 + 行为规则]       ← 整个会话不变  
    [CLAUDE.md 项目配置]       ← 项目级，基本不动  
    ────── 缓存断点在这里 ──────  
    [对话历史 + 工具调用结果]   ← 每轮追加，动态变化  
    [当前用户输入]              ← 永远是新的

[p011]
前面几层，每次请求都是完全相同的 token 序列，缓存稳稳命中。后面两层是动态追加的，不参与缓存，按全价计费。一次 30 分钟的会话，你只在最开始为那 20,000 token 的静态内容付一次"写入"费用。之后每一轮，它都以 $0.30/MTok 的缓存读取价格出现，而不是 $3.00/MTok 的全价。分摊下来，边际成本趋近于零。这也回答了另一个问题：为什么 Claude Code Pro 能做到每月 $20？一次会话写入一次，后面几十轮都在"以 1/10 的价格"复用同样的内容，加上动态部分的全价计费，总成本就降到了一个月付费订阅可以覆盖的范围。

[p013]
五、让缓存崩掉有多容易？理解了前缀匹配的机制，你就会明白，缓存其实是一件"容易坏"的东西。案例一：两个大写字母，2700 token 全废有人做过实验，连发三条请求，前两条系统提示一样，第三条把 "senior software engineer" 改成 "Senior Software Engineer"。结果第三条请求，2,727 个缓存 token 全部作废，完全重算。两个大写字母，干掉了整份缓存。这不是 bug，这是机制本身。token 序列变了，哈希就变了。案例二：时间戳放错了位置HN 上有个用户发帖说自己一直莫名其妙地缓存命中率极低，后来查出来是因为他在系统提示的顶部加了一行当前时间戳。每次请求时间都不同，哈希永远对不上，缓存永远 miss。把时间戳挪到最底部，命中率立刻涨了 20 个百分点。案例三：中途切模型缓存是按模型隔离的。你用 Sonnet 跑了一半，突然切到 Opus，之前积累的整个缓存对 Opus 完全不可见，从零开始。案例四：超时了默认 TTL 是 5 分钟，中间回复了几条微信、接了个电话，6 分钟后回来，缓存过期，下一次请求触发全量重建，成本一下子回到了第一轮。案例五：resume 的 bug去年 3 月，社区里有人发现 Claude Code 的 \--resume 功能存在缓存 bug，主要原因是工具定义的排列顺序在 resume 后不稳定，导致缓存 key 每次都不一样。命中率从正常的 97% 以上跌到 4%—17%，相当于每次都在全价重算，成本高出 10 到 20 倍。这个 bug 从 3 月 4 日引入，4 月 1 日修复，持续了整整 28 天。

[p015]
六、如果你自己在搭 Agent，该怎么做？Prompt Caching 的规则是固定的，但怎么用是你的选择。把 Claude Code 的设计逻辑拿过来用就行。原则一：静态内容前置，动态内容后置工具定义、系统提示、文档资料——一旦确定就不要动，放最前面。用户输入、每轮的工具调用结果——只能追加，放最后面。不要在静态区域里加时间戳、随机数、会话 ID 这类每次都变的东西。原则二：注意 token 最低阈值Anthropic 的 API 有最低缓存门槛，不同模型略有差异，通常在 1,024 token 左右。如果你的系统提示太短，加了 cache_control 也没用，系统会默默跳过，不报错。自建应用的时候要注意这个下限。原则三：Compaction 要"缓存安全"跑了很多轮之后，上下文会撑到快满，需要压缩历史。这时候的正确做法是：保持系统提示、工具定义、对话历史前缀完全不变，把压缩指令作为一条新消息追加进去。绝对不能改动前面已经缓存的部分，否则一次压缩会把整个缓存打废。原则四：监控命中率一个正常运转的会话，缓存命中率计算方式：

[p016]
命中率 = cache_read_tokens / (cache_read_tokens + cache_creation_tokens + input_tokens)

[p017]
每次 API 响应里都会有这三个字段。健康的活跃会话，这个数字应该在 90% 左右。如果长期低于 70%，一定有什么东西在频繁打断你的缓存前缀，值得排查。

[p019]
七、92% 这个数字的意义回到开头的问题。92% 的缓存命中率，意味着你每发出去的 100 token，只有 8 token 是真正在"做新事情"，剩下 92 token 都是以 1/10 价格复用的旧计算。这不是什么黑科技，也没有特别复杂的算法。它的背后是一个极其朴素的工程判断：把不变的东西和会变的东西分开，让不变的东西尽可能长时间地保持稳定。整个 Claude Code 的产品架构在做的事情，用一句话说就是：不惜一切代价，保持前缀稳定。Prompt 的结构顺序是策略，工具定义的加载时机是策略，compaction 的方式是策略，甚至是否允许用户在会话中途切换模型——背后都是同一个约束在驱动。很多做 AI 应用的团队，早期都把精力放在 prompt 怎么写、上下文怎么组织、RAG 怎么搭。这些当然重要。但如果在成本控制这件事上没有形成系统性的工程习惯，跑起来之后的账单会让人很难受。Prompt Caching 大概是 LLM 工程领域最接近"免费午餐"的优化手段了——前提是你得先把"什么不能变"这件事想清楚。

[p021]
如果你在用 Claude Code 或者自己搭 Agent，建议把 API 响应里的 cache_read_input_tokens 字段监控起来，这个数字会告诉你很多。
