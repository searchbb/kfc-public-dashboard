# Delphi Digital：代理经济的瓶颈并非支付，而是「交接与验收」

[p003]
编译：AididiaoJP，Foresight News

[p004]
Agent 电商讨论已有两年，支付环节率先落地。Stripe 让 Agent 能够向商家付款，Coinbase 的 x402 提供了稳定币结算通道，按次购买数据与推理服务已经跑通。但任务一旦超出「调用一次接口」，问题便随之改变：Agent 无法独立完成，需将部分环节外包，并确认对方确实完成了约定工作。

[p005]
Delphi 这篇文章聚焦的正是这一环节。任务市场并非另一个支付协议，而是让 Agent 将无法完成的部分外包：先明确交付物，再开始执行，成果被接受后才放款。若交接可靠，任务便可继续推进，无需将用户拉回充当项目经理，逐段对接供应商。

[p006]
买输入与买结果，并非一回事

[p007]
房东筛选租客时，Agent 可向现成服务商调取信用记录与驱逐记录。对方返回标准材料，房东据此判断。此时购买的是决策输入，任务终点仍在房东手中。

[p008]
房产税复议则不同。Agent 可比较周边成交，发现评估可能偏高，但这一发现不会自动修改税单。真要推进，通常需找熟悉县内流程的人递交材料、出庭。任务市场要帮助 Agent 找到此人，并事先明确工作方式与结算条件。

[p009]
前者接近当前按次付费：价格清晰，交付物标准化，验收几乎自动完成。后者购买的是一桩办完的事。材料提交不等于案件就绪，回执也不等于合格。付款条件必须挂钩「可验收的结果」，而非「对方声称做过」。

[p010]
这也是任务市场与普通 API 市场的分界：API 市场出售调用；任务市场出售经确认的完工单元。

[p011]
任务定义不清，市场难以运转

[p012]
能进入任务市场的任务，需先定义到双方都清楚资金与何种结果挂钩。专家完全可能提交一份质量很差的复议材料，同时附上一张回执。若买方支付的是「一份合格材料」，就必须有人在放款前审核材料。

[p013]
由谁审核、任一方如何对审核结果提出异议，最好事先写入订单。如此，买方不怕收到劣质交付，接单方也不怕对方无理拒付。缺少这一层，市场会滑向两个坏方向：要么买方随意拒付，专业供给不愿进入；要么提交表面成果即可拿钱，买方下次不敢发单。

[p014]
任务太小也不划算。审核与争议处理成本若高于外包节省的成本，人们会改回自己完成，或继续只用标准化接口。因此，早期更可能出现在边界清晰、可重复、验收有据的任务上，而非一次性模糊委托。

[p015]
企业会是更合适的早期买方。它们本就在多家供应商之间拆分任务，内部已有流程与对照标准。Agent 可在公司内备好任务，再将必须外包的环节发出去，拿回的结果还能与现有流程核对。若任务反复出现，接单方也能积累某类任务的完成记录。声誉一旦可累积，下一次匹配便无需从零建立信任。

[p016]
个人用户并非不能用，但早期更像样板。企业有预算、有复购、有内部验收习惯，更接近市场冷启动所需的订单密度。

[p017]
支付只解决付款，雇人仍缺验收

[p018]
把钱打出去，与将一单任务雇出去，中间隔着托管、交付、验收、异议。Stripe 与 x402 覆盖的是前半段。Agent 仍需找到人去递交复议、代表业主。没有验收，支付越方便，错误订单也可能走得越快。

[p019]
现有产品已按这一结构搭建。

[p020]
Daydreams 的 TaskMarket 由买方发单、Agent 接单。买方先将资金打入，可让工人直接认领，也可先看方案再选人。资金放在托管中，提交成果被接受后才放款。

[p021]
Virtuals 的 Agent Commerce Protocol 由委托方 Agent 与接单方 Agent 谈好任务，资金进入托管，交付并通过审批后放款。还可加入外部评估人，核查成果是否符合事先约定。NEAR 一侧也在将任务、预算、竞标与验证整合为一套流程，方向同样是「为完工的任务定价」，而非只为一次调用定价。

[p022]
几家路径不完全相同，但骨架接近：发单、匹配、托管、提交、验收、放款。缺少验收，托管只是延迟转账；有了验收，托管才成为对结果的约束。

[p023]
有人将验收单写得更细：需写清委托内容、接单方、价格、验证人、交付物、异议窗口、退款状态。单据越完整，Agent 之间才能交接，而不必将用户重新变为调度员。

[p025]
任务市场被提出，不仅因为外包听起来高级，更因为多步流程会放大误差。十步任务，每步正确率 95%，全部走完不出错的概率约只剩六成。每多一次无人验收的交接，前面的错误就会带入下一环节。

[p026]
因此，市场需在交接处设置检查点：这一环节通过，再购买下一环节。错误停在当步，而非一路滚到最后才发现整单作废。对 Agent 尤其如此。它不像公司员工，出问题可开会追责；它需要事先写好的验收条件与放款规则。

[p027]
这也解释了为何当前 Agent 交易大多仍停留在加密原生与简单服务：任务短、结果易验、纠纷少。真正拉开差距的，是将多家供应商串入更长工作流，并在每一步把关。

[p028]
当前看到的是骨架，而非规模

[p029]
任务市场要做的事很具体：让 Agent 将部分任务外包，成果被认可后再付款，从而将更多任务真正完成。支付层已经具备。缺的是可验证的完工单元、成本可接受的验收，以及足够密集的重复订单。

[p030]
公司内部流程向外延伸，会是第一批像样的需求。个人侧的复杂委托，需等验收成本与纠纷处理先降下来。在此之前，更值得关注的不是又一个支付协议，而是三件事能否同时出现：任务能否被写成可验收的单据，托管能否在过审前扣住资金，接单方是否有可累积的完工记录。

[p031]
这三件齐备，Agent 才有机会将任务做完，而非做到一半，再将用户叫回来继续当项目经理。
