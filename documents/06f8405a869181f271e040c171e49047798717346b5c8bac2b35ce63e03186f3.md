[p014]
## 什么是 AI Agent？

[p015]
在讲可观测性之前，先要知道 AI Agent 是什么。

[p016]
AI Agent 是一个使用 LLM 来规划、调用工具、并自主完成任务的系统。

[p017]
简单说，LLM 只会输出文本。但 AI Agent 不止于此。它能思考、调工具、读文件、搜网页、跑代码，走很多步来达成目标。

[p018]
比如我们问 Agent："帮我找周五从德里到班加罗尔最便宜的航班，然后订票。"

[p019]
Agent 会思考要做什么，调用航班搜索工具，读取结果，挑最便宜的，调用订票工具，最后给我们确认单。

[p020]
Agent 在中间做了很多步，我们只看到最终结果。

[p021]
这就是 Agent 的威力。它让生活变简单。

[p022]
但正因为它走了很多步、执行很多操作，内部发生了大量我们从外面看不到的事情。这就是为什么需要可观测性。

[p023]
## 什么是可观测性？

[p025]
Observability = Observe + Ability

[p026]
可观测性就是通过系统产生的数据，观察系统内部发生了什么的能力。

[p027]
简单说，可观测性让我们能回答："我的系统现在在干什么，为什么这样干？"

[p028]
假设汽车发出奇怪的声音。我们打开仪表盘看速度、油量、引擎温度。从这些信号，我们能理解引擎内部的状况，不用拆开整个引擎。

[p029]
仪表盘给了我们对汽车的可观测性。

[p030]
医生对人体做同样的事。医生看不到身体内部，所以用 X 光、血检、心跳监测。从这些信号，医生理解内部发生了什么。

[p031]
软件的可观测性也是同样的道理。我们从运行中的系统收集信号，从这些信号理解它的内部状态。

[p032]
## 什么是 AI Agent 可观测性？

[p033]
AI Agent 可观测性是记录和理解 AI Agent 内部每一步操作的实践，让我们能看到它为什么这样行为。

[p034]
简单说，AI Agent 在给出最终答案前走了很多隐藏的步骤。

[p035]
可观测性把这些隐藏步骤打开，让我们能看到每一次思考、每一次工具调用、每一个决策。

[p036]
回到订票 Agent。

[p037]
从外面我们只看到最终消息："您的航班已订好。" 但内部发生了很多事：

[p038]
*   
Agent 思考任务
  *   
Agent 用某些输入调用航班搜索工具
  *   
搜索工具返回航班列表
  *   
Agent 选择一个航班
  *   
Agent 调用订票工具
  *   
订票工具返回确认单

[p039]
AI Agent 可观测性记录所有这些隐藏步骤。

[p040]
所以出错时，我们不用猜。只需打开记录，看到每一步到底发生了什么。

[p041]
把它想象成飞机上的黑匣子。

[p042]
黑匣子记录飞行期间的一切。出问题时，我们打开黑匣子，准确理解发生了什么。

[p043]
AI Agent 可观测性就是 Agent 的黑匣子。

[p044]
## 为什么需要 AI Agent 可观测性？

[p045]
![Image](assets/AI%20Agent%20%E5%8F%AF%E8%A7%82%E6%B5%8B%E6%80%A7%E5%AE%8C%E5%85%A8%E6%8C%87%E5%8D%97-9bd14779b1/03-image.png)

[p046]
AI Agent 很强大，但也很不可预测。

[p047]
同一个 Agent 对同一个任务可能走不同路径。

[p048]
它调用真实的工具、花真实的钱、发真实的邮件、和真实的用户交互。

[p049]
所以 Agent 失败时，失败藏在很多步骤的某个地方。没有可观测性，我们完全是盲的。

[p050]
假设用户投诉："Agent 订错了航班。"

[p052]
*   
LLM 误解了用户意图？
  *   
Agent 用错误的日期调用搜索工具？
  *   
搜索工具返回了错误数据？
  *   
Agent 从正确列表里选错了航班？
  *   
订票工具失败了，Agent 忽略了？

[p053]
没有可观测性，我们回答不了任何问题。只能猜，猜不是工程。

[p054]
我们需要 AI Agent 可观测性的主要原因：

[p055]
*   
看到 Agent 从头到尾走的每一步
  *   
找到 Agent 出错的准确位置
  *   
追踪每个任务花了多少钱、用了多少 token
  *   
追踪 Agent 的速度
  *   
捕获错误、重试、失败的工具调用
  *   
理解 Agent 为什么做某个决策
  *   
在生产环境实时监控 Agent，出问题时获得告警
  *   
收集真实数据，后续用来改进 Agent

[p057]
## AI Agent 可观测性和传统可观测性有什么区别？

[p058]
我们做普通软件的可观测性已经很多年了。

[p059]
所以问题来了：为什么 AI Agent 需要特殊的可观测性？

[p060]
答案是 AI Agent 的行为和普通软件非常不同。

[p061]
普通软件中，相同输入总是给相同输出。

[p062]
如果调用一个函数 2 + 2，总是返回 4。路径是固定的。行为是可预测的。

[p063]
但 AI Agent 是非确定性的。

[p064]
这意味着相同输入可能给出不同输出，每次走不同路径。

[p065]
Agent 今天可能走 3 步，明天对同一任务走 6 步。

[p066]
它可能这次调用工具，下次跳过。

[p067]
而且普通软件中，错误通常很清楚。程序要么工作，要么崩溃并报错。

[p068]
但 AI Agent 可能静默失败。

[p069]
它能给出看起来完美但完全错误的答案。

[p070]
没有崩溃，没有红色错误。

[p072]
我把传统可观测性和 AI Agent 可观测性的区别列个表，方便你理解需要额外追踪什么：

[p073]
传统可观测性| AI Agent 可观测性  
---|---  
相同输入给相同输出| 相同输入可能给不同输出  
固定的执行路径| 每次运行路径都变  
错误是明确的崩溃| 失败可能静默且看起来正确  
我们追踪 CPU、内存、请求| 我们还追踪 token、成本、工具调用、推理  
我们主要检查"它运行了吗？"| 我们还检查"答案好吗？"  
日志是简单文本行| 我们还捕获 prompt、响应、决策

[p074]
所以，AI Agent 可观测性包含传统可观测性的一切，外加很多 Agent 特有的新东西。

[p075]
## 可观测性的三大支柱

[p076]
可观测性建立在三个经典支柱上。这三个支柱来自传统软件，也适用于 AI Agent。

[p077]
1\. 日志（Logs）

[p078]
日志是发生事件的简单文本记录。对 Agent 来说，日志可以是这样一行："Agent 调用了航班搜索工具，参数是周五从德里到班加罗尔。"

[p079]
2\. 指标（Metrics）

[p080]
指标是随时间测量的数字。对 Agent 来说，指标可以是用了多少 token、每个任务的成本、平均耗时。

[p081]
3\. 追踪链路（Traces）

[p082]
Trace 展示一个请求在系统中移动的完整旅程，一步一步。

[p083]
对 Agent 来说，trace 展示一个任务中的每次思考、每次工具调用、每次 LLM 调用。

[p084]
对 AI Agent 来说，trace 是最重要的支柱。

[p085]
因为 Agent 内部做了太多步骤，我们必须看到完整旅程才能理解它的行为。所以我们详细理解 trace。

[p086]
## Trace 和 Span

[p087]
这两个词，trace 和 span，是 AI Agent 可观测性的核心。

[p088]
我们用简单例子理解它们。

[p089]
Span 是 Agent 内部一个单独步骤或操作的记录。

[p090]
Trace 是 Agent 一次完整运行的完整记录，由很多 span 组成。

[p091]
简单说，span 是一个步骤，trace 是由很多步骤组成的整个故事。

[p092]
回到订票 Agent。当用户让 Agent 订票时，发生一次完整运行。

[p093]
那次完整运行是一个 trace。

[p094]
在那个 trace 里，每个小步骤是一个 span：

[p095]
*   
Span 1: Agent 收到用户请求
  *   
Span 2: LLM 思考并决定搜索航班
  *   
Span 3: Agent 调用航班搜索工具
  *   
Span 4: Agent 读取搜索结果
  *   
Span 5: LLM 选择最便宜的航班
  *   
Span 6: Agent 调用订票工具
  *   
Span 7: Agent 返回最终确认

[p096]
所以这一个 trace 有 7 个 span。

[p097]
每个 span 记录有用的细节，比如输入、输出、耗时、任何错误。

[p098]
Span 还可以嵌套。比如一个"规划" span 里面可以包含一个"LLM 调用" span。

[p099]
这种嵌套形成树状结构，这棵树展示了 Agent 工作的完整结构。

[p100]
我们可以把一个 trace 想象成这样：

[p101]
TRACE: 订一张从德里到班加罗尔的机票  
    │  
    ├── SPAN: 收到用户请求  
    ├── SPAN: 规划任务  
    │       └── SPAN: LLM 调用（决定搜索航班）  
    ├── SPAN: 工具调用（航班搜索）  
    │       ├── 输入: 德里 -> 班加罗尔，周五  
    │       └── 输出: 12 个航班列表  
    ├── SPAN: 选择最便宜的航班  
    │       └── SPAN: LLM 调用（选航班）  
    ├── SPAN: 工具调用（订票）  
    │       └── 输出: 订票确认  
    └── SPAN: 返回最终确认

[p102]
这里能看到，trace 是完整的树，每个分支是一个 span。

[p103]
有些 span 里面还包含更小的 span。

[p104]
看这棵树，我们一眼就能理解 Agent 的整个旅程。

[p105]
Trace 就像一次就诊的完整医疗报告，每个 span 就像报告里的一项单独检查。

[p106]
合在一起，它们讲述完整故事。

[p108]
当用户和 Agent 长时间对话时，整个对话可能有很多 trace，用户每发一个请求就有一个。

[p109]
我们把所有这些 trace 归到一个 session 里。

[p110]
所以完整的画面很简单：一个 session 包含很多 trace，每个 trace 包含很多 span。

[p111]
我们可以把这个层次结构想象成这样：

[p112]
SESSION（一次完整用户对话）  
    │  
    ├── TRACE 1（请求："找航班"）  
    │       ├── SPAN: LLM 调用  
    │       └── SPAN: 工具调用（搜索）  
    │  
    └── TRACE 2（请求："订第一个航班"）  
            ├── SPAN: LLM 调用  
            └── SPAN: 工具调用（订票）

[p113]
这里能看到，session 是最大的盒子，trace 在里面，span 在每个 trace 里面。

[p114]
## Agent 内部应该观测什么？

[p115]
现在我们理解了 trace 和 span，

[p116]
下一个问题是：每个 span 里到底应该捕获什么？

[p117]
AI Agent 有很多运动部件。我们必须观测每一个。我们逐个过一遍。

[p120]
每次 Agent 和 LLM 对话，我们必须捕获发送的完整 prompt、收到的完整响应、模型名称、控制创造性的 temperature 设置、输入 token 数、输出 token 数、成本。

[p121]
这帮助我们理解 Agent 在想什么，花了多少钱。

[p123]
Agent 用工具采取行动。

[p124]
每次工具调用，我们必须捕获调用了哪个工具、传了什么输入、返回了什么输出、成功还是失败。

[p125]
大多数时候，Agent 失败是因为调用了错误的工具或传了错误的输入。

[p126]
所以这个数据非常宝贵。

[p127]
3\. 推理和规划步骤

[p128]
Agent 经常在行动前思考。

[p129]
我们必须捕获这个推理过程，这样能理解 Agent 为什么选择某个行动。

[p131]
很多 Agent 使用记忆来记住过去的步骤或过去的对话。

[p132]
我们必须观测 Agent 从记忆里读了什么、写了什么。

[p134]
有时工具失败，Agent 重试。

[p135]
我们必须捕获每次重试和每个错误，这样知道 Agent 在哪里挣扎。

[p137]
最后，我们必须捕获 Agent 给用户的最终答案，这样能检查是否正确和有帮助。

[p138]
当我们捕获所有这些，就得到了 Agent 的完整画面。没有任何东西被隐藏。

[p139]
## AI Agent 可观测性的关键指标

[p140]
捕获 trace 告诉我们每次运行的完整故事。

[p141]
但我们还需要能随时间追踪的数字。这些数字叫指标。看看必须追踪的关键指标。

[p142]
延迟（Latency）

[p143]
Agent 完成任务需要的时间。我们必须追踪总时间，也要追踪每一步的时间。

[p144]
一个慢的工具或慢的 LLM 调用会让整个 Agent 变慢。

[p146]
Agent 每个任务用的 token 数。Token 是 LLM 读写的文本小块。更多 token 意味着更高成本。

[p148]
我们为每个任务花的钱。因为 Agent 做很多 LLM 调用，成本可能增长很快。

[p151]
Agent 完成任务走了多少步。

[p152]
如果 Agent 走太多步，它在浪费时间和钱，或者陷入了循环。

[p154]
成功的工具调用百分比。

[p155]
低成功率意味着工具或 Agent 的某个地方坏了。

[p157]
Agent 遇到错误的频率。上升的错误率是出问题的早期预警。

[p159]
这是最重要的指标。它告诉我们 Agent 正确完成任务的频率。

[p160]
通过随时间观察这些指标，我们能快速发现 Agent 什么时候开始变差。

[p161]
## AI Agent 可观测性的工作原理

[p162]
![Image](assets/AI%20Agent%20%E5%8F%AF%E8%A7%82%E6%B5%8B%E6%80%A7%E5%AE%8C%E5%85%A8%E6%8C%87%E5%8D%97-9bd14779b1/05-image.png)

[p163]
现在理解可观测性在实践中如何工作。

[p164]
这个过程有几个简单部分。

[p165]
步骤 1: 埋点（Instrumentation）

[p166]
首先，我们给 Agent 添加埋点。

[p167]
埋点意味着添加小段代码来记录 Agent 在每一步做什么。

[p168]
简单说，我们在 Agent 每个重要位置放置微小的传感器。

[p169]
这些传感器记下输入、输出、时间、任何错误。

[p170]
最好的是，大多数现代 Agent 框架已经内置了这个埋点，所以我们不用自己写太多代码。

[p172]
Agent 运行时，埋点产生 trace、span 和指标。

[p173]
这些数据被收集并发送到可观测性平台。

[p174]
步骤 3: 存储和连接数据

[p175]
平台存储所有 span 并把它们连接成完整的 trace。

[p176]
所以一次运行的所有步骤被归到一起，成为一个清晰的故事。

[p177]
步骤 4: 可视化数据

[p178]
平台在仪表板上展示这些数据。

[p179]
我们能把每个 trace 看成 span 的树。可以点击任何 span 查看准确的 prompt、响应、工具输入、工具输出。

[p182]
所以如果成本突然跳升、或错误率上升、或 Agent 变慢，我们立刻收到通知。

[p183]
我们可以把整个流程想象成这样：

[p184]
AI AGENT（带埋点）  
    │   记录每一步  
    ▼  
    Trace、Span 和指标  
    │   发送到  
    ▼  
    可观测性平台  
    （存储并连接 span 成完整 trace）  
    │  
    ├───────────────────┐  
    ▼                   ▼  
    仪表板              告警  
    （看每一步）        （在高成本、错误、  
                         慢时通知我们）

[p185]
能看到，整个流程很简单：记录一切、收集、连接、展示、告警。

[p186]
这里有个很重要的标准是 OpenTelemetry。

[p187]
OpenTelemetry 是开源标准，定义了如何用通用格式收集 trace、指标和日志。

[p188]
因为它是通用标准，我们可以收集一次数据，发给很多不同工具。

[p189]
这就是为什么大多数可观测性工具支持 OpenTelemetry。

[p190]
OpenTelemetry 现在甚至有专门的 GenAI 约定。

[p191]
这些给 AI 特定的东西提供标准名称，比如模型名、token 数、成本。

[p192]
所以每个工具用同样方式读取它们，我们不用担心每个工具对同一个东西用不同名称。

[p193]
## 可观测性和评测工具

[p194]
现在看看一些帮助我们做 AI Agent 可观测性的流行工具。

[p195]
我们不用从头构建一切。这些工具提供开箱即用的追踪、仪表板和告警。

[p196]
*   
LangSmith \- LangChain 团队构建的可观测性和评测平台。提供每个 Agent 步骤的详细 trace。
  *   
Langfuse \- LLM 应用和 Agent 的开源可观测性平台。捕获 trace、成本和指标。
  *   
Arize Phoenix \- 基于 OpenTelemetry 构建的 LLM 应用追踪和评测开源工具。
  *   
OpenTelemetry \- 用通用格式收集 trace、指标和日志的开放标准。
  *   
Laminar \- 开源、OpenTelemetry 原生平台，专门为追踪长运行 Agent 构建，不只是单次 LLM 调用。
  *   
Datadog 和 Grafana \- 传统可观测性平台，现在也支持 LLM 和 Agent 监控。

[p197]
我们可以根据用例选择这些工具。很多支持 OpenTelemetry，所以不会被锁定在一个工具上。

[p198]
## 可观测性 vs 评测

[p199]
人们经常混淆可观测性和评测。

[p200]
我们要搞清楚，因为它们不同，但会一起工作。

[p201]
可观测性告诉我们 Agent 做了什么。

[p202]
评测告诉我们做得有多好。

[p203]
简单说，可观测性记录每次运行的完整故事。

[p204]
评测然后判断那个故事是不是好故事。

[p205]
假设订票 Agent 订了一张票。可观测性展示它订票走的每一步。

[p206]
评测检查它是否选了最便宜的航班、用了正确日期、正确完成了任务。

[p208]
它给我们原始数据。然后评测用那些数据给 Agent 打分。

[p210]
没有可观测性，我们没有东西可评测。

[p211]
没有评测，我们的可观测性数据没有对质量的判断。

[p212]
## AI Agent 可观测性的挑战

[p213]
AI Agent 可观测性很强大，但也有一些挑战。我们必须意识到它们。

[p214]
*   
海量数据：Agent 走很多步，所以产生巨量 trace 数据。存储和搜索这些数据可能变得很贵。
  *   
敏感数据：Prompt 和工具输入可能包含用户隐私信息。我们必须小心隐藏或掩盖这些敏感数据。
  *   
非确定性行为：因为 Agent 每次走不同路径，很难直接比较两次运行。
  *   
可观测性本身的成本：记录一切会增加一些额外时间和成本。我们必须平衡记录多少。
  *   
连接步骤：在有很多子 Agent 的复杂 Agent 中，很难把所有 span 连接成一个干净的 trace。需要良好的埋点来保持故事完整。
  *

[p216]
最后看看 AI Agent 可观测性的一些最佳实践。

[p217]
这些会帮助我们获得最大价值。

[p218]
*   
从第一天就追踪一切。不要等出问题才添加可观测性。构建 Agent 时就加上。
  *   
捕获完整 prompt 和响应。不要只记"调用了 LLM"。记录实际输入和输出，这样后续能调试。
  *   
使用像 OpenTelemetry 这样的通用标准。这保持灵活性，避免被锁定在一个工具上。
  *   
追踪每次运行的成本和 token。Agent 成本增长快，所以从一开始就监控。
  *   
掩盖敏感数据。存储 trace 前总是隐藏用户隐私信息。
  *   
设置告警。让告警在出问题时通知你。
  *   
把可观测性和评测连接起来。用收集的 trace 给 Agent 打分并改进。
  *   
保留过去运行的 trace。它们帮助你发现模式并随时间改进 Agent。

[p219]
如果遵循这些实践，我们总是能知道 Agent 在做什么，为什么这样做。

[p220]
这就是 AI Agent 可观测性如何帮助我们把神秘的黑盒 Agent 变成清晰、可理解、

[p221]
可信任、可调试、可改进的系统。

[p222]
现在我们应该理解了 AI Agent 可观测性，为什么需要它，

[p223]
必须观测什么，trace 和 span 的核心概念，必须追踪的指标，以及可以用的工具。
